# How It Works

Every hand-off in the factory seems to reduce to the same five things, and [The Five Primitives](primitives.md) names them: a digest-bound statement, a delegated verdict, a capability descriptor, trust configuration, and freshness state. Fix those five and the choice of tools becomes close to arbitrary -- swap Syft for Trivy and what changes is which binary emits the SBOM attestation, and everything downstream should still read the same format.

[The Hand-offs](handoffs.md) spends the primitives on the boundaries that need them. Most boundaries inside a factory are ordinary function calls. I count five that are trust-domain transitions, where the receiver's only evidence about what the sender did is a signature. Those five are where the architecture lives, and each one needs its own key, policy and audit trail. Everything else is plumbing.

Then the contract. [Slots and Outcomes](slots.md) defines each component position by the outcome it owes -- a signed SBOM, a reviewed diff, a scanned artefact -- so the tool that fills it becomes an implementation detail. It also covers how an implementation declares machine-readably what it can actually do, and why that contract belongs in a Kubernetes custom resource: the API server rejects a bad slot declaration on admission, and the core can ask the cluster which implementation is installed and how to call it. Big Bang carries the same information too, spread across a 2,653-line values file, the template conditionals that read it, and whatever those templates happened to render. Nothing checks a bad declaration on admission there, and as far as I can tell there is nothing left to query afterwards.

The count of five is the claim on this page I'd least like to bet on. A sixth trust-domain boundary would arrive with its own key, its own policy and its own way of going wrong, so it matters whether I've got the number right. If you can see one I've missed, where is it?
